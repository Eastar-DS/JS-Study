# 브라우저 렌더링 파이프라인 스터디

## 발표: 브라우저는 화면을 어떻게 그리는가

### 1. HTML 문서 받아오기

브라우저는 HTML 파일을 읽기 위해 만들어진 도구입니다. 외부에 있는 HTML을 받아오기 위해 네트워크를 통해 가져오게 됩니다.

특정 웹 페이지에 들어가서 네트워크 탭을 보면, 가장 먼저 `Document`라는 항목이 오는 것을 확인할 수 있습니다. 이것이 바로 HTML 파일입니다.

### 2. DOM과 CSSOM 만들기

HTML 파일을 받아온 이후에는 한 줄씩 읽어 내려갑니다. HTML 파일은 `head`와 `body`로 구성되어 있는데, 차근차근 읽어 내려가다가 `head`에서 스타일시트 링크(CSS 파일)를 만나면 해당 파일을 다운로드합니다.

이 과정을 정리하면 다음과 같습니다.

- HTML을 한 줄씩 읽어 내려가면서 동시에 **DOM 트리**를 만듭니다.
- CSS 파일도 다운로드가 완료되면 한 줄씩 읽어가며 **CSSOM 트리**를 만듭니다.
- 두 작업은 **병렬적으로** 진행됩니다.

> CSSOM은 "씨에스에스 오엠" 또는 "씨솜" 두 가지로 모두 발음할 수 있습니다.
> 

### 3. 렌더 트리 만들기

DOM과 CSSOM이 모두 만들어지면, 이제부터는 DOM을 차근차근 순회하면서 CSSOM에서 CSS 정보를 하나씩 가져옵니다. 그리고 이를 매핑시킵니다.

최종적으로 **렌더 트리(Render Tree)**가 만들어지는데, 여기에는 화면에 보이는 요소만 남깁니다(예: `display: none`인 요소는 제외됩니다).

### 4. 레이아웃(Layout)

렌더 트리가 만들어지면 이제부터는 화면을 그리기 시작합니다. 첫 단계는 **레이아웃**입니다.

레이아웃은 이름에서 알 수 있듯이 위치를 잡아주는 단계입니다. 뷰포트(viewport)를 기준으로 화면에 어떤 모양으로 어떻게 보일지를 결정합니다.

- **싱글 스레드**로 동작합니다.

### 5. 페인트(Paint)

페인트 단계에서는 어떻게 그릴지를 결정합니다. 배경 색상 같은 시각적 속성들을 처리합니다.

### 6. 합성(Composite)

마지막으로 **합성** 단계가 있습니다. 합성 단계에서는 레이아웃과 페인트 과정을 거친 결과물을 화면에 그리는 단계입니다.

---

## 동적인 변경이 일어날 때

요즘 웹사이트는 가만히 있지 않고 굉장히 동적으로 움직입니다. 무언가 변경되면 필요한 부분에서 레이아웃, 페인트, 혹은 합성만 진행하는 식으로 동작합니다.

- **레이아웃**은 실제로 레이아웃이 바뀐 경우에 동작합니다.
- **페인트**는 색상이나 `visibility` 같은 속성이 바뀐 경우에 동작합니다.
- **합성**도 단독으로 동작할 수 있습니다.

레이아웃은 싱글 스레드이고, 레이아웃 단계를 거치면 그다음 페인트와 합성 단계를 무조건 거쳐야 합니다. 그래서 레이아웃까지 가게 되면 비용이 비싸집니다.

게다가 위치가 바뀐 경우 그 요소만 영향을 받는 것이 아니라, 형제 요소나 자식 요소까지 영향을 주는 경우가 많습니다. 그래서 계산 비용이 굉장히 커집니다.

따라서 **레이아웃까지 가지 않도록 만들어주는 것이 최적화의 방향**이 될 수 있습니다.

## 질문과 토론

### Q1. 뷰포트 기준의 수치 계산은 어느 단계에서 일어나는가?

레이아웃에서 뷰포트를 기준으로 수치를 계산한다고 했는데, 이를 **Computed Style**이라고 부르는 것 같습니다. 자료를 찾아보니 렌더 트리를 만들면서 같이 한다는 설명도 있어서 정확히 어디에 위치하는지 헷갈렸습니다.

이 부분은 브라우저마다 구현이 다릅니다. 따라서 명확하게 단언하기는 어렵지만, 전체적인 과정은 위에 설명한 순서대로 진행된다고 보면 됩니다.

### Q2. 요소나 구조가 변경되면 DOM과 CSSOM부터 다시 만들어야 하는가?

찾아본 결과, 동적으로 스타일이 변경될 때는 **CSSOM에 반영이 되지 않습니다**. 렌더 트리를 만들 때 스타일 계산을 하면서 **Computed Style 객체**를 생성하고 붙이는데, 변경 사항은 거기에만 반영됩니다.

즉, 다음과 같이 정리할 수 있습니다.

- DOM은 변경된 부분만 삽입/삭제됩니다.
- CSSOM은 바뀌지 않습니다.
- 렌더 트리에 변경 사항이 반영됩니다.

> Blink 엔진을 기준으로 보면, 렌더 트리는 특정 객체로 이루어져 있습니다. 레이아웃 계산을 하면 그 정보가 렌더 트리의 객체 안에 저장되고, 마지막에 그려질 때는 렌더 트리만 보고 그릴 수 있는 구조입니다. 스타일, 레이아웃 위치, 페인트 정보가 모두 거기에 들어갑니다.
> 

### Q3. 개발자 도구의 Elements 탭은 무엇을 보여주는가?

개발자 도구에서 보는 것은 **DOM 트리**입니다. 다만 단순한 DOM 트리가 아니라 계산된 스타일(Computed Style)이 결합된 형태입니다.

근거로, CSS의 가상 선택자(`::before`, `::after`)로 만든 가상 요소(Pseudo Element)가 개발자 도구에는 표시됩니다. 이런 가상 요소는 DOM에는 존재하지 않고 CSS로만 설정되는데, 개발자 도구에서는 보이는 이유는 DOM 트리에 계산된 스타일 정보가 결합되어 표시되기 때문입니다.

### Q4. 리플로우는 왜 거의 항상 최상위부터 일어나야 하는가?

해당 요소가 변경될 때 형제 노드나 자식 요소가 영향을 받는 것은 자연스럽습니다. 그런데 부모 요소도 자식 요소(예: `fit-content` 등)에 영향을 받을 수 있습니다. 이렇게 영향이 타고 올라가다 보면 결국 전체를 다시 보는 선택이 합리적이라고 합니다.

진짜로 변경된 요소만 정확히 찾아서 리플로우하면 비용이 더 적을 것 같지만, 형제·자식뿐 아니라 부모 요소로도 영향이 갈 수 있는 경우의 수가 많습니다. 그것들을 하나하나 추적하는 비용이 그냥 전체를 다시 보는 비용보다 더 컸을 것이라는 답변을 받았습니다.

### Q5. React의 Virtual DOM은 리플로우를 최적화하는가?

결론부터 말하면 **아닙니다**. Virtual DOM은 브라우저의 렌더링 동작 자체를 변경할 수 없습니다. Virtual DOM이 해결하는 것은 **DOM 업데이트의 최소화**입니다.

예를 들어 다음과 같은 컴포넌트가 있다고 가정해 봅시다.

```jsx
function ItemList({ items }) {
  return (
    <ul>
      {items.map(item => <li key={item.id}>{item.name}</li>)}
    </ul>
  );
}
```

배열의 요소가 하나 추가되었을 때, 코드상으로는 리스트 전체를 다시 그리는 것처럼 작성합니다(선언적). 하지만 실제로는 추가된 하나만 DOM에 삽입됩니다.

만약 이를 절차적으로 작성한다면 "어떤 요소가 추가되었는지 확인하고 그 위치에 끼워 넣는" 코드를 직접 작성해야 했을 것입니다. Virtual DOM은 **선언적인 작성 방식의 비용을 줄여주는 것**이지, 브라우저의 리플로우 범위를 직접 통제하는 것은 아닙니다.

### Q6. 레이아웃이 일어나면 페인트와 합성이 반드시 일어나는가?

- **페인트**: 거의 항상 필요합니다.
- **합성**: 경우에 따라 생략되거나 최소화될 수 있습니다.

다만 추가로 알게 된 점은 다음과 같습니다.

- 화면 밖(뷰포트 바깥)에 있는 요소는 레이아웃만 바뀌고 페인트가 미뤄지거나 생략될 수 있습니다.
- `visibility: hidden`도 비슷하게 최적화될 수 있습니다.

또한 **강제 레이아웃**이 발생하는 경우가 있습니다. `offsetWidth` 같은 속성을 읽으면 배치 시스템이 중간에 멈추고 즉시 레이아웃을 계산합니다. 이런 경우 그다음 단계인 페인트는 그 시점에 같이 일어나지 않습니다(다음 프레임에서 처리됨).

### Q7. 합성 단계의 특징

- *별도의 스레드(Compositor Thread)**에서 동작하므로 메인 스레드 부담이 적습니다.
- **GPU 가속**이 가능한 속성들이 있어, 이 속성들은 합성 단계에서만 동작하면 되므로 성능이 좋습니다.
- `transform`이나 애니메이션 가속이 여기에 해당합니다.
- `z-index`로 분리된 레이어와 관련이 있습니다.

### Q8. DOM 트리와 CSSOM 트리를 따로 만드는 이유

**병렬 처리를 위해서**입니다. 두 트리를 따로 만들면 동시에 파싱할 수 있어 속도가 빨라집니다.

4. 레이아웃/리플로우가 일어나면 무조건 페인트/합성이 일어나야 하나?
    - **Layout → Paint는 거의 필수**
        - 거의??? 필수 아닌 경우는 언젠데
        - 화면(뷰포트) 밖에 있는 요소는 Paint가 생략되거나 미루어질 수 있음
        - 또는 offsetWidth 등 사용하면서… 아래 예제
        
        ```tsx
        더 좋은 예시는 스크립트가 레이아웃 값을 강제로 읽지만, 프레임 전에 다시 원상복구하는 경우입니다.
        
          box.style.width = '200px'
        
          console.log(box.offsetWidth) // 여기서 강제 layout 가능
        
          box.style.width = '100px'
        
          이 경우 흐름은 대략 이렇습니다.
        
          width 변경
          -> offsetWidth 읽기
          -> 최신 값 필요
          -> Style/Layout 강제 수행
          -> 이후 width 원복
          -> 최종 프레임에서는 시각적 변화 없음
          -> Paint가 생략될 수 있음
        ```
        
    - **Layout → Composite는 조건부**
    - **Composite-only 업데이트도 존재**
5. 리플로우를 진짜 변경된 요소들만 추적해서 하면 안 될까? 그런 브라우저가 없는 이유가 궁금하다
