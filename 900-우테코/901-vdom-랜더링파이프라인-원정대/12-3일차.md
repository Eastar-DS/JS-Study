# "렌더 단계와 커밋 단계는 왜 나뉘어 있나?"
### 큰 줄기 (가장 자주 인용되는 분류)

```text
Trigger        : 업데이트 발생 (setState 등)
   ↓
Render Phase   : 가상 DOM 생성 + diff
   ↓
Commit Phase   : 실제 DOM 변경
   ↓
Browser Paint  : 브라우저가 화면 그림 (← React 영역 아님)
```
리액트 공식 문서도 "**Trigger → Render → Commit**"의 세 단계로 설명합니다. 이 중 React가 직접 책임지는 건 **Render와 Commit 두 단계**.

### Commit Phase 안을 더 쪼개면

```text
Commit Phase
  ├─ Mutation     : 실제 DOM 변경 (insert/update/remove)
  ├─ Layout       : useLayoutEffect, ref 콜백 실행
  └─ Passive      : useEffect 실행 (Paint 후 비동기)
```

근데 처음에는 이걸 다 나누지 말고 **"Render와 Commit 두 단계"** 로 잡으면 충분

## 왜 두 단계로 나뉘어 있는가? — 핵심 4가지 이유
### 이유 ① 끊을 수 있는 것과 없는 것을 분리

```text
Render Phase  : 메모리상의 작업 (가상 DOM만 변경, DOM 안 만짐)
                → 중간에 끊어도 화면에 영향 없음 ✓ 끊을 수 있음

Commit Phase  : 실제 DOM 변경 작업 (부수효과)
                → 중간에 끊으면 화면이 깨진 상태로 남음 ✗ 끊을 수 없음
```

이 둘을 분리해야 **Render만 시간 단위로 쪼갤 수 있음**. Fiber의 동시성(concurrency)의 기반.

### 이유 ② 일관성 보장 (두 트리 시스템)

리액트는 두 개의 가상 DOM 트리를 동시에 관리합니다.

```text
Current tree         : 현재 화면에 그려진 상태의 가상 DOM
WorkInProgress tree  : 지금 만들고 있는 새 가상 DOM
```

```text
Render Phase  : WIP tree를 천천히 만듦 (current는 그대로)
                ↓
Commit Phase  : WIP가 완성되면 current와 swap (한 번에)
                ↓
사용자 시점   : 항상 current tree만 보임
                "만들어지는 중인 깨진 상태"는 절대 안 보임
```

만약 두 단계가 합쳐져 있으면, render 도중에 화면이 부분적으로 갱신되면서 **사용자가 깨진 중간 상태를 볼 수 있음**. 분리 덕분에 **"all or nothing"** 보장.

### 이유 ③ 취소 가능

진행 중인 render가 더 긴급한 업데이트로 **무효화**될 수 있어요.

```text
사용자: 검색어 "react" 입력
React: render 진행 중...

사용자: "react " 추가 입력 (긴급 업데이트)
React: "이전 render 결과는 더 이상 의미 없음. 폐기."
       새 render 시작
```

Render Phase는 메모리 작업이니 **버려도 안전**. DOM은 아직 안 만졌으니까.

만약 Render와 Commit이 합쳐져 있으면? DOM을 절반쯤 갱신하다 취소하면 화면이 망가짐. 분리 덕분에 자유롭게 취소 가능.

### 이유 ④ Layout Thrashing 차단

이전에 정복한 내용 — 분리 덕분에 **"모든 쓰기를 모아서 commit 시점에 한 번에"** 패턴이 자연스럽게 강제됩니다.

```text
직접 DOM:    쓰기 → 읽기 → 쓰기 → 읽기 → ... (thrashing)
React:       모든 쓰기 (commit 한 번) → 그 후 읽기 (effect)
```

## 답변
### 1. Fiber의 동시성
리액트는 메인 스레드 한 개 위에서만 돌아가니 Parallel은 불가능. **Concurrent**는 가능.
```text
[React 16+ — Concurrent]
업데이트 A 시작 → 일부 → 양보 → 일부 → 양보 → 끝
                       ↑              ↑
                       사용자 입력!   ← 긴급 업데이트로 A 중단 가능
                       업데이트 B 시작 → 처리 → 끝 → A 재개

  - A 진행 중 B가 끼어들 수 있음
  - 우선순위 따라 A를 잠시 멈추고 B 먼저
  - "여러 업데이트가 동시에 진행 중인 상태"
```

### 동시성이 가능하게 하는 능력 4가지

```text
1. 끊기 (Interruptible)
   진행 중인 render를 시간 부족으로 잠시 멈춤

2. 재개 (Resumable)
   멈췄던 render를 다음 프레임에 이어서

3. 폐기 (Discardable)
   진행 중이던 render를 버리고 새로 시작

4. 우선순위 (Prioritized)
   여러 업데이트 중 어떤 걸 먼저 할지 결정
```
이 모든 능력이 **"render는 메모리 작업이라 버려도, 끊어도, 다시 시작해도 안전"** 하다는 사실에서 옴. 그래서 이스타가 정확히 짚었듯, **render와 commit 분리가 동시성의 기반**이 됩니다.



### 2. 잘못된 가정 — "한 프레임 안에 commit 해야 한다"

**아닙니다.** Render가 끝나야 commit. 한 프레임 안에 render가 안 끝나면 **commit을 미룹니다.**

## 질문 
1. 리액트는 메인 스레드 한 개 위에서만 돌아간다고했는데, 이건 JS엔진의 싱글스레드를 말하는거야? 
2. 렌더와 커밋을 구분한 이유가 fiber의 동시성을 위한거야? 리액트 16버전부터 fiber의 동시성이 가능해진거니까 렌더와 커밋을 구분한 이유가 아니라 렌더와 커밋을 구분해서 얻을 수 있는 장점같아. 렌더와 커밋을 구분한 핵심 이유를 알고싶어. 
3. 양보가 뭘말하는지 모르겠어. 현재 진행중인 작업이 무거운거 같으면 다른작업부터 진행하라고 양보한다는건가? 
4. fiber가 길어진 동작을 단위별로 쪼갠다고 생각했는데 그게 아닌건가? fiber가 뭔지부터 다시 알아야할듯?

### 2. 진짜 핵심 이유 — 선언형 패러다임의 본질

가상 DOM 자체가 다음 두 단계를 가지는 게 자연스러움:

```text
1. "이렇게 그려달라"는 선언 (개발자가 적은 JSX)
   → 가상 DOM 생성/비교 = Render
   
2. 그 결과를 실제 화면에 반영
   → DOM 변경 = Commit
```

이건 **선언형 프로그래밍의 본질**입니다. "결과를 선언하면 라이브러리가 차이를 계산해 반영"이라는 모델 자체가 두 단계로 나뉘어 있음.

분리의 핵심 이유는 **선언형 모델에서 "변경 계산"과 "변경 적용"이 본질적으로 두 일이기 때문**. 그 분리가 부수효과 격리, batching, thrashing 차단을 가능하게 했고, 나중에 동시성까지 가능하게 만든 것.

### 분리에서 자연스럽게 따라온 4가지 결과

분리한 결과 얻은 장점들:

```text
1. Side Effect 격리
   render는 순수 함수여야 함 (같은 입력 → 같은 결과)
   commit은 부수효과 (DOM 변경, ref 콜백)
   둘을 분리하지 않으면 render가 비순수해짐
   → React mental model의 기초

2. Batching 자연스럽게 가능
   여러 setState를 모아 한 번 render → 한 번 commit
   "쓰기를 모아서 한 번에"의 본질

3. Layout Thrashing 차단
   render에서는 DOM 안 만짐 → 강제 동기 layout 없음
   commit에서 한 번에 적용

4. (React 16+ 추가) 동시성 가능
   render만 끊을 수 있게 만듦
   ← 이게 이스타가 짚은 "분리해서 얻은 장점"
```


### 4. Fiber의 두 가지 의미

```text
1. fiber 노드 (자료구조)
   = 컴포넌트 하나에 대응하는 JS 객체
   = 작업 단위 하나
   
   예시 구조:
   {
     type: 'Header',         // 컴포넌트 타입
     stateNode: <DOM>,       // 실제 DOM 참조
     child: <자식 fiber>,
     sibling: <형제 fiber>,
     return: <부모 fiber>,
     pendingProps: ...,      // 새 props
     memoizedProps: ...,     // 이전 props
     flags: ...,             // 변경 플래그 (insert, update, delete)
   }

2. Fiber (아키텍처/시스템 이름)
   = React 16+의 reconciliation 엔진 이름
   = "fiber 노드들을 단위로 작업을 쪼개서 처리하는" 시스템
```

```text
React 16+ (Fiber Reconciler):
  fiber 노드를 연결 리스트로 순회 → 끊을 수 있음
  현재 fiber 포인터만 저장하면 재개 가능
```


## Q1. 한 프레임 안에 다 못 살펴보면, 비교 완료된 fiber만 반영?

**아닙니다. React는 "all-or-nothing" 원칙을 지킵니다.**

```text
한 프레임 안에 render 완료 못 함
  → commit 미룸
  → 사용자 화면: 이전 current tree 그대로 (변화 없음)
  → 메모리: WIP tree 계속 만드는 중
  
다음 프레임에 render 마저 끝남
  → Commit 한 번에 (current ⇄ WIP swap)
  → 사용자 화면: 새 상태로 갱신
```

**왜 일부만 commit하면 안 되나?** 일관성이 깨지기 때문.

```jsx
// 예시: 부모-자식이 한 묶음으로 갱신되어야 의미가 있는 컴포넌트
function UserCard({ user }) {
  return (
    <div>
      <Avatar src={user.avatarUrl} />
      <Name text={user.name} />
      <Email text={user.email} />
    </div>
  );
}
```

만약 한 프레임에 Avatar와 Name까지만 commit되고 Email은 다음 프레임에 commit된다면?

```text
사용자가 보는 중간 상태:
  새 Avatar (User B)
  새 Name (User B)
  이전 Email (User A)  ← 깨진 상태
```

이런 깨진 상태가 **사용자에게 절대 보이면 안 된다**는 게 React의 약속입니다.

```text
React의 보장:
  사용자가 보는 화면 = 항상 일관된 상태 (current tree)
  WIP는 메모리 안에서만 존재 → 사용자 절대 못 봄
  Commit은 atomic (한 번에 전체)
```

**정리**: 이스타의 추측은 합리적이지만 React는 그 길을 안 갔어요. **"일관성 > 빠른 반영"** 을 선택했습니다.

## Q2. 모든 트리 노드는 다 살펴봐야 하고, 끊고 양보할 수 있는 장점만?

**정확합니다.** 이게 Fiber의 본질을 정확히 잡은 문장이에요.

```text
Fiber가 안 줄여주는 것:
  - 처리해야 할 작업의 총량
  - render가 모든 변경된 fiber를 다 살펴봐야 한다는 사실

Fiber가 추가한 것:
  - 끊을 수 있는 능력 (interruptible)
  - 재개할 수 있는 능력 (resumable)
  - 폐기할 수 있는 능력 (discardable)
  - 우선순위 기반 스케줄링
```

비교로 보면:

```text
React 15 (Stack Reconciler):
  총 100ms 작업 → 100ms 동안 메인 스레드 독점
  사용자 입력/스크롤 모두 멈춤

React 16+ (Fiber):
  총 100ms 작업 → 5ms씩 나눠서 처리
  매 5ms 사이마다 양보 → 입력 처리, 화면 갱신
  완료까지는 여전히 100ms (또는 약간 더 길어질 수 있음)
  하지만 그 사이 화면이 멈추지 않음
```

**작업 효율은 비슷하거나 약간 안 좋아짐 (양보 오버헤드). UX는 천지차이 좋아짐.**

이스타가 짚은 핵심 — "**중간중간 끊고 브라우저에 일을 맡길 수 있는 정도의 장점**" — 정확합니다. Fiber는 마법으로 작업을 줄이는 게 아니라, 같은 작업을 사용자에게 덜 거슬리게 처리하는 도구.

여기에 **추가 보너스**:

- 진행 중인 render를 폐기 가능 → 더 긴급한 업데이트 즉시 처리
- 우선순위 표현 가능 (useTransition 등)

## Q3. setState는 순수함수에 포함 안 되니 render와 다른 개념?

**정확합니다.** 매우 중요한 분리예요.

### Render는 순수해야 한다 — 무슨 뜻?

```text
"순수 함수" 의미:
  같은 입력(props, state) → 같은 결과(JSX)
  외부 상태 변경 X
  부수효과 X (DOM 조작, API 호출, setState 등)
```

```jsx
// ✅ 순수한 컴포넌트 (render 함수)
function Greeting({ name }) {
  return <h1>안녕 {name}!</h1>;
}
// 같은 name이면 항상 같은 결과
```

### setState는 render 안에서 호출하면 안 됨

```jsx
// ❌ render 도중에 setState 호출
function Bad() {
  const [count, setCount] = useState(0);
  setCount(count + 1);  // 무한 루프
  return <div>{count}</div>;
}
// → 렌더 → setCount → 다음 렌더 → setCount → ... 무한
```

### setState는 어디서 호출하나?

```text
✓ 이벤트 핸들러 안 (onClick 등)
✓ useEffect / useLayoutEffect 안
✓ 비동기 콜백 (fetch.then, setTimeout 등)

✗ render 함수 본문 (특수한 경우 제외)
✗ 컴포넌트 함수의 일반 흐름
```

### setState의 정체

```text
setState는 "render의 일부"가 아니라
"다음 render를 예약하는 트리거"
```

```text
[흐름]
사용자 클릭
  ↓
이벤트 핸들러 실행 (render 외부)
  ↓
setState(newValue) 호출
  ↓
React: "이 컴포넌트 다시 render해야 함" 표시
  ↓
스케줄러가 다음 render 예약
  ↓
다음 render 시작 (순수 함수로 실행)
  ↓
가상 DOM 생성 → diff → commit
```

이스타의 표현 정확합니다 — **setState는 render와 별개의 개념**. Render의 외부 트리거이지, render 자체가 아님.

이게 React의 mental model에서 가장 중요한 한 점:

```text
"render는 무엇을 그릴지 선언하는 것 (순수)
 setState는 다시 그려달라고 요청하는 것 (트리거)"
```

이 분리가 명확해야 useEffect 의존성 배열, 클로저, stale value 같은 후속 개념들이 풀립니다.

## Q4. Render와 Commit을 더 자세히 — 학습 지도 2단계

이게 다음 i+1입니다. 1단계(큰 그림) 정복했고, 이제 2단계(내부 메커니즘)로.

### 2단계 학습 지도

```
A. Render Phase 내부
   - 가상 DOM 생성과 비교 (diff)
   - Fiber 트리 순회 순서 (depth-first, beginWork → completeWork)
   - 작업 단위와 시간 체크
   - 변경 플래그 누적 (effects list)

B. Commit Phase 내부
   - 세 하위 단계 (Mutation / Layout / Passive)
   - 실제 DOM 변경 시점
   - useLayoutEffect / ref 콜백 시점
   - useEffect는 언제?

C. 두 트리 시스템 (current / workInProgress)
   - 왜 두 개를 둬야 하는가
   - 이중 버퍼링과 비슷한 패턴
   - Commit에서 swap하는 메커니즘
```

A부터 시작하는 게 자연스럽습니다.

### 2단계-A 미션 — Render Phase 내부

자료가 짧으니 먼저 정리해드릴게요. 읽고 자기 언어로 답하는 미션은 그 다음.

**Render Phase 내부 핵심 흐름**

```text
1. 트리거: setState 등으로 업데이트 발생
   → React: "어디부터 render 해야 하나" 결정 (보통 root부터)

2. WorkInProgress 트리 만들기 시작
   → root fiber부터 깊이 우선(DFS) 순회

3. 각 fiber에서 두 단계
   beginWork(fiber)    : 자식까지 내려가며 처리
                          - 컴포넌트 함수 호출 (= 렌더 함수 실행)
                          - 결과로 자식 fiber들 생성
                          - 변경 플래그 표시 (insert/update/delete)
   
   completeWork(fiber) : 자식 다 끝나고 부모로 올라오며 처리
                          - 자식의 변경 사항을 부모로 전파
                          - DOM 노드 미리 생성 (아직 부착 X)

4. 각 단위 사이마다 시간 체크 → 부족하면 양보

5. 트리 순회 완료 → effects list 완성
   = "어떤 fiber에 어떤 변경을 적용해야 할지" 목록
   = Commit Phase가 이 목록을 보고 실제 DOM 변경
```

**핵심 그림**

```text
순회 순서 (DFS, beginWork → completeWork):

       App ①
        │
       Header ②          ← beginWork(App), beginWork(Header)
        │
       Logo ③            ← beginWork(Logo)
        ↑
        │ completeWork(Logo)
        │
       Header ④          ← completeWork(Header)
        ↑
        │
       Content ⑤         ← beginWork(Content)
        │
       Item ⑥            ← beginWork(Item)
        ↑
        │ completeWork(Item)
        │
       Content ⑦         ← completeWork(Content)
        ↑
        │
       App ⑧             ← completeWork(App) → render 끝
```

이 순회 중간에 시간 부족하면 멈춤, 다음 프레임에 재개.

# 10분 질문

1. 가상돔 만들 때 사용하는 createElement는 webAPI 인가? 아니면 React api 인가? @Eastar
  2. createElement를 재귀적으로 실행하면서 vdom을 만든다. 이때 재귀적으로 실행한다면 자식부
  터 만들어지는 것이 아닌가?

### 1.
React API입니다.
`React.createElement("div", null, "hello")`
  이건 실제 DOM을 만드는 게 아니라, React가 이해할 수 있는 React Element 객체, 흔히 말하는
  VDOM에 가까운 객체를 만듭니다.

  반대로 Web API는 이겁니다.
  `document.createElement("div")`
  이건 브라우저가 제공하는 DOM API이고, 실제 DOM 노드를 만듭니다.

  즉 이름은 비슷하지만 완전히 다릅니다.
React.createElement("div")
  // React API
  // 결과: JS 객체

  document.createElement("div")
  // Web API
  // 결과: 실제 DOM Element


### 2. 
상황을 두 가지로 나눠야 합니다.
```
<div>
    <span>Hello</span>
  </div>
```

  대략 이렇게 됩니다.

```
  React.createElement(
    "div",
    null,
    React.createElement("span", null, "Hello")
  )
```

```
React.createElement("span", null, "Hello") // 먼저 실행
  React.createElement("div", null, spanElement) // 나중 실행
```

  즉 JSX가 중첩된 React.createElement 호출로 변환된 경우에는 자식 element 객체가 먼저 만들어
  지고, 부모 element 객체가 나중에 만들어집니다.

하지만 “재귀적으로 만든다”는 표현은 구현 방식에 따라 다릅니다.

  예를 들어 직접 이런 함수를 만들었다면:

```
  function createElement(type, props, children) {
    return {
      type,
      props,
      children: children.map(child =>
        typeof child === "object"
          ? createElement(child.type, child.props, child.children)
          : child
      )
    };
  }
```

  이 경우에는 부모 createElement 함수가 먼저 호출되고, 함수 내부에서 자식들을 재귀적으로 처리
  합니다. 그래서 호출 진입은 부모부터, 완성되는 객체는 자식부터라고 볼 수 있습니다.


React는 부모의 자식들을 JSX에 적힌 순서대로 배열에 넣습니다.
리스트도 마찬가지입니다.

 ```
  <ul>
    {items.map(item => <li>{item.name}</li>)}
  </ul>
 ```

  items가:

  ["a", "b", "c"]

  이면 children 순서도:

  [li(a), li(b), li(c)]
