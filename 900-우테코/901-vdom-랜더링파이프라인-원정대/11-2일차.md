# 야생학습 주제
"리액트는 1회차에서 본 비싼 작업을 어떻게 다루나?”

"리액트가 우리가 직접 DOM을 조작하는 것보다 나은 점이 있다면 그건 무엇 때문인가?”

"리액트는 1회차에서 본 비싼 작업을 줄이려고 어떤 구조를 갖고 있나?”

# 공부 내용

## 첫 답변
"비싼 작업을 어떻게 다루나?" → 아래 4 카테고리 전체
"직접 DOM보다 나은 점?" → 주로 A (자동으로 최소 변경 계산)
"어떤 구조를 갖고 있나?" → 주로 C (Fiber 아키텍처)

A. DOM 조작 횟수 줄이기 — "Layout/Paint 트리거 자체를 줄이자"
1. Virtual DOM (가상 DOM)
실제 DOM의 가벼운 JS 객체 복제본을 메모리에 둠
상태가 바뀌면 메모리에서 새 가상 DOM을 만들고 이전 것과 비교
진짜 DOM에는 차이나는 부분만 반영
→ DOM API 호출 횟수 ↓ → Layout/Paint 트리거 ↓
"innerHTML 1000번 vs 한 번에"의 자동화 버전

2. Reconciliation (재조정)
이전 가상 DOM과 새 가상 DOM을 비교하는 알고리즘
휴리스틱: "같은 타입 컴포넌트는 같은 자리에서 props만 갱신, 다른 타입이면 통째로 교체"
O(n³)이 아닌 O(n)으로 동작하기 위한 가정

3. Key Prop
리스트에서 각 항목을 식별하는 고유 키
키가 없으면 인덱스 기반 매칭 → 항목 추가/제거 시 엉뚱한 재사용 발생
키 정확히 주면 최소 변경으로 리스트 업데이트

---

B. 재렌더 빈도 줄이기 — "필요할 때만 렌더하자"
4. Batching (일괄 처리)
한 이벤트 핸들러 안에서 setState를 여러 번 호출해도 한 번만 렌더
React 18부터는 setTimeout, Promise.then 안에서도 자동 batching
→ 불필요한 재렌더링 ↓

5. Memoization (memo, useMemo, useCallback)
변경 안 된 컴포넌트/값/함수를 재사용
React.memo: props가 같으면 컴포넌트 스킵
useMemo: 계산 결과 캐싱
useCallback: 함수 참조 안정화
→ 불필요한 재계산/재렌더 ↓ (단, 남용하면 비용이 더 큼)

6. Selective Re-rendering
리액트는 컴포넌트 단위로 렌더링
상태가 바뀐 컴포넌트와 그 자식만 다시 렌더 (부모는 안 함)
memo로 자식의 재렌더도 끊을 수 있음

---

C. 메인 스레드 점유 시간 줄이기 — "긴 JS 작업이 화면을 막지 않게"
7. Fiber (React 16+ 내부 아키텍처)
가상 DOM 비교 작업을 작은 단위(fiber 노드) 로 쪼갬
한 번에 다 처리하지 않고 중간중간 렌더 기회를 브라우저에 양보
→ "JS Task 하나가 길어지면 화면이 멈춘다"는 step5.5의 문제 해결
step5.5/02 requestAnimationFrame의 패턴을 라이브러리 차원에서 자동화

8. Concurrent Features (useTransition, useDeferredValue)
업데이트의 우선순위를 표현 가능
사용자 입력(긴급) > 무거운 리스트 갱신(낮은 우선순위)
사용자가 타이핑 중인데 무거운 검색 결과 갱신 때문에 입력이 막히는 문제 해결

--- 

D. 첫 화면 렌더링 빠르게 — "Critical Rendering Path 단축"
9. Code Splitting (React.lazy + Suspense)
첫 화면에 필요 없는 코드는 나중에 로드
첫 JS 번들 크기 ↓ → Critical Rendering Path 빠르게
step7의 defer/async 사용자 자동화 버전

10. SSR / Server Components (선택적)
서버에서 미리 HTML을 만들어 보냄
사용자가 첫 화면을 빠르게 보고, 그 위에 JS를 hydrate
step7의 "첫 화면 빨리 보이기" 문제 해결

## 답변
A. DOM 조작 횟수 줄이기
1. "여러 요청을 모아서 한번만 DOM 업데이트?"
부분적으로 맞고, 약간 다릅니다. 두 개념이 헷갈려 있어요.


Batching        : 여러 상태 변경을 모아서 "한 번의 렌더링"으로 처리
Virtual DOM     : 그 한 번의 렌더링 안에서 "이전 결과 vs 새 결과를 비교해
                  진짜 바뀐 부분만 실제 DOM에 반영"
직접 DOM을 다룬다고 상상해보세요:


// 직접 DOM
list.innerHTML = '';                    // 다 지우고
items.forEach(item => {                  // 다시 다 만듦
  const li = document.createElement('li');
  li.textContent = item.text;
  list.appendChild(li);
});

// Virtual DOM 사용 (개념)
// 1. 이전 가상 DOM과 새 가상 DOM을 비교
// 2. "3번째 li의 텍스트만 바뀜"을 알아냄
// 3. 진짜 DOM에는 그 li 하나의 textContent만 변경
→ DOM API 호출 횟수 자체가 줄어듦. Layout/Paint 트리거가 줄어듦.

2. "리액트는 DOM 업데이트할 부분을 자동으로 찾아주나?"
그렇습니다. 그게 핵심 가치예요.

직접 DOM이라면 개발자가 매번 "어디를 어떻게 바꿔야 하나"를 계산해야 합니다. 리액트는 "이번에 화면이 어떻게 보여야 하는지" 만 적으면(JSX), 리액트가 알아서 차이를 계산해 DOM을 업데이트합니다.


// 개발자는 "결과"만 적음
function Counter({ count }) {
  return <div>{count}</div>;
}
// 리액트가 알아서: count가 5→6일 때 그 텍스트만 갱신
3. "Reconciliation은 가상돔과 실제 돔의 차이?"
아니요. 가상 DOM과 가상 DOM의 차이입니다. 이게 핵심.


이전 가상 DOM   ──비교──   새 가상 DOM
                  ↓
              차이점 목록
                  ↓
            실제 DOM에 반영
            (이게 마지막 단계)
Reconciliation은 두 가상 DOM 트리 비교까지가 일이고, 그 결과를 실제 DOM에 반영하는 건 별개 단계(commit phase)입니다.

4. "휴리스틱이 뭐?"
완벽하지는 않지만 대부분 충분히 좋은 답을 내는 경험 기반 규칙입니다.

두 트리를 완벽히 비교하면 알고리즘 비용이 O(n³). 노드 1000개면 10억 번 비교. 비현실적.

리액트는 "몇 가지 가정"을 두고 O(n)으로 줄임:

같은 위치에 다른 타입이면 통째로 교체 (속까지 비교 안 함)
같은 위치에 같은 타입이면 props만 비교
완벽한 비교는 아니지만 99% 케이스에서 충분히 정확.

5. "타입이 뭐고, 같은 타입 같은 자리 props 갱신은 무슨 뜻?"
타입 = 컴포넌트 종류 (<Button>, <Input>, <div>)


// 케이스 1: 같은 위치, 같은 타입
이전: <Button label="저장" />
새:   <Button label="완료" />
→ 같은 Button 인스턴스 유지, label prop만 갱신
→ 컴포넌트의 state, DOM도 그대로 (label만 변경)

// 케이스 2: 같은 위치, 다른 타입
이전: <Button label="저장" />
새:   <Input value="..." />
→ Button 통째로 제거 + Input 새로 생성
→ 안의 state, DOM, 이벤트 리스너 다 새로
이스타의 표현 "컴포넌트 안의 구성요소들 중 일부분만 바꾼다" — 정확합니다.

6. "리스트가 뭐? 키 정확히 주면?"
리스트 = 반복 렌더링되는 항목들 (배열을 map으로 그릴 때).


{items.map(item => <li>{item.text}</li>)}
key 없을 때: 리액트는 인덱스로 매칭.


이전: [A, B, C]   →   인덱스 0=A, 1=B, 2=C
새:   [X, A, B, C] (맨 앞에 X 추가)

리액트는 인덱스로 보면:
  0: A → X (텍스트 갱신)
  1: B → A (텍스트 갱신)
  2: C → B (텍스트 갱신)
  3: (새로 추가) C
→ 모든 li를 다 갱신
key 있을 때: 리액트는 key로 매칭.


이전: [A(key=a), B(key=b), C(key=c)]
새:   [X(key=x), A(key=a), B(key=b), C(key=c)]

리액트는 key로 보면:
  key=x: 새로 추가
  key=a, b, c: 그대로
→ X만 추가, 나머지 그대로
→ "props만 갱신"과는 다른 차원입니다. "이 항목이 추가/이동/제거됐는지" 를 정확히 추적하는 도구가 key.

B. 재렌더 빈도 줄이기
1. "Batching = 여러 상태 요청을 한 렌더링으로 묶는 거?"
정확합니다. 한 이벤트 핸들러 안에서 setState를 여러 번 호출해도 한 번만 렌더.


function handleClick() {
  setCount(c => c + 1);     // 보통이면 렌더 1번
  setName('foo');            // 또 렌더?
  setVisible(true);          // 또 렌더?
}
// 실제: 세 setState를 묶어서 렌더링은 한 번만
React 18부터는 setTimeout/Promise 안에서도 자동 batching.

2. "React.memo — props 안 바뀌면 자동 아닌가?"
여기가 가장 중요한 오해 풀어야 할 지점입니다.

리액트의 기본 동작은 "부모가 재렌더되면 자식도 무조건 재렌더" 예요. props가 안 바뀌었어도!


function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>{count}</button>
      <Child name="foo" />   {/* count 바뀔 때마다 Child도 재렌더 */}
    </>
  );
}
왜 이렇게 동작? 리액트는 props가 바뀌었는지 매번 비교하는 비용을 피하려고 그냥 "재렌더"가 기본. 비교는 옵션.


기본 동작 흐름:
  Parent 재렌더
    → Child의 가상 DOM 다시 생성
      → Reconciliation으로 이전 가상 DOM과 비교
        → 같으면 실제 DOM은 안 바뀜 (이건 효율적)
        → 단, 가상 DOM 생성 + 비교 비용은 발생
React.memo의 역할: 이 첫 단계(가상 DOM 다시 생성)를 건너뛰는 것.


const Child = React.memo(function Child({ name }) {...});

// 이제는 Parent가 재렌더되어도 Child의 props가 같으면
// Child 함수 자체를 호출 안 함 → 가상 DOM 생성도 안 함
→ Reconciliation에서 제거가 아니라 그 이전 단계(가상 DOM 생성)를 스킵.

3. "useCallback의 함수 참조 안정화?"
JS에서 함수는 객체라서, 같은 코드라도 다시 만들면 다른 참조입니다.


function Parent() {
  // 매 렌더마다 새 함수가 만들어짐
  const handleClick = () => doSomething();
  
  return <Button onClick={handleClick} />;
}
매 렌더마다 handleClick은 다른 함수 객체. Button의 onClick prop이 "매번 다르다"고 보임.

문제: Button을 React.memo로 감싸도 onClick이 매번 다르니 메모가 안 작동.


const Button = React.memo(function Button({ onClick }) {...});
// 위 Parent에서 Button은 매 렌더마다 다시 렌더됨 (onClick이 다른 참조니까)
해결: useCallback으로 같은 함수 참조 유지.


const handleClick = useCallback(() => doSomething(), []);
// deps([])가 안 바뀌면 같은 함수 객체 재사용
→ "같은 코드의 함수를 같은 객체로 유지하는 도구".

4. "Selective Re-rendering이 다른 개념과 반복되는 거 같은데?"
예리한 관찰입니다. 이 셋은 같은 큰 우산 아래의 도구들이에요.


큰 우산: "필요한 만큼만 렌더하기"

  ├─ Selective Re-rendering : 기본 원리 (자동 동작)
  │    "상태 바뀐 컴포넌트와 그 자식만 재렌더"
  │
  ├─ Batching              : 같은 이벤트 안의 setState를 묶기 (자동)
  │    "한 핸들러의 setState 여러 번 → 렌더 한 번"
  │
  ├─ React.memo            : 자식 재렌더 끊기 (개발자가 선택)
  │    "props 같으면 자식 함수 호출 자체 스킵"
  │
  └─ useMemo / useCallback  : memo가 작동하도록 props 안정화
       "객체/함수 참조를 같게 유지"
Selective Re-rendering은 리액트가 항상 하는 기본 동작(별도 메커니즘이 아님)이고, 나머지(memo, useMemo, useCallback, batching)는 그 기본 동작을 더 효율적으로 만드는 도구들입니다.

이 구조를 머릿속에 그려두면 헷갈림이 줄어요.

정리 — 카테고리 안 흐름

A 카테고리 (DOM 조작 줄이기)
  Virtual DOM         : "결과만 적으면 차이를 자동으로 찾아줌"
  Reconciliation      : 그 차이 찾는 알고리즘 (휴리스틱 사용)
  Key                 : 리스트에서 항목 식별 도구

B 카테고리 (재렌더 빈도 줄이기)
  Selective Re-render : 리액트의 기본 원리 (자동)
  Batching            : 같은 이벤트의 setState 묶기 (자동)
  memo                : 자식 재렌더 끊기 (수동)
  useMemo/useCallback : memo가 작동하도록 props 안정화 (수동)

## 답변
1. 왜 일반 트리 비교가 O(n³)?
알 필요는 없습니다. "완벽한 알고리즘은 비싸다, 그래서 우회한다"는 사실만 알면 충분해요. 그래도 직관만:

일반적인 트리 편집 거리(Tree Edit Distance) 문제 — "트리 A를 트리 B로 바꾸는 최소 편집 횟수"를 찾는 알고리즘.

n³가 되는 이유:


1) 한 트리의 모든 노드 vs 다른 트리의 모든 노드 매칭 검사
   → n × n = O(n²)

2) 각 매칭마다 "부분 트리를 어떻게 바꿔야 최소인가" 결정
   → 추가로 O(n)

→ 총 O(n²) × O(n) = O(n³)
핵심은 "노드가 트리 안에서 어느 위치로든 이동할 수 있다" 는 가능성을 다 고려하는 것. 그래서 비싸짐.

2. 휴리스틱이 어떻게 O(n)으로 줄임?
O(n³)의 두 큰 비용을 가정으로 잘라냅니다.

잘라내는 비용 1 — "노드 이동 추적" 제거
리액트는 같은 위치(부모 안의 같은 자리)만 비교합니다. 노드가 트리 안에서 다른 위치로 옮겨가는 경우는 추적하지 않음.


// 이전
<div>
  <Header />
  <Footer />
</div>

// 새
<div>
  <Footer />   {/* 사실은 Header가 사라지고 Footer가 위치 변경 */}
  <Header />
</div>
리액트는 "Footer가 이동했다"고 인식하지 않습니다. 그냥 "0번 자리: Header→Footer로 바뀜, 1번 자리: Footer→Header로 바뀜" 으로 보고 둘 다 다시 만들어요. 이게 아까 본 "같은 위치" 휴리스틱.

→ 모든 노드가 모든 위치로 이동할 가능성을 검사하는 O(n²) 비용이 사라짐.

잘라내는 비용 2 — "부분 트리 안까지 비교" 제거
다른 타입이면 그 안은 안 봅니다. 부분 트리 통째로 교체.


// 이전
<Counter>
  <Display />
  <Buttons>
    <PlusButton />
    <MinusButton />
  </Buttons>
</Counter>

// 새
<Display />
리액트는 <Counter> → <Display>로 타입이 다르니 Counter 안의 자식들을 일절 비교 안 합니다. 그냥 Counter 트리 통째로 제거 + Display 새로 생성.

→ 부분 트리 깊이만큼의 추가 비교 O(n) 비용이 사라짐.

결과
위 두 가정으로, 트리 비교가 단순한 위에서 아래로의 트리 순회로 줄어듭니다.


일반 알고리즘: 모든 노드를 모든 위치와 매칭 + 부분 트리 비교 → O(n³)

리액트:       각 노드를 같은 위치의 노드 한 번만 비교
              + 다른 타입이면 안쪽 안 봄
              → 트리 한 번 순회로 끝 → O(n)
대가: 위 첫 예시처럼 "Header와 Footer가 자리 바꾼 경우"를 인식 못하고 둘 다 다시 만듭니다. 휴리스틱은 "완벽함"을 포기하고 "실용적 속도"를 얻은 거예요.

이 대가의 일부를 보완하는 게 key입니다. key를 주면 형제들 사이에서는 "이 항목이 위치 이동했다"를 인식할 수 있게 돼요.

3. 이게 diffing 알고리즘인가?
그렇습니다. 정확히는 다음과 같이 구분됩니다.


Diffing 알고리즘     : "두 가상 DOM 트리의 차이를 찾는 부분"
                      ← 위 휴리스틱이 핵심

Reconciliation       : "찾은 차이를 실제 DOM에 반영하는 전체 과정"
                      = Diffing + Commit (실제 DOM 업데이트)
엄밀히 나누면 위와 같지만, 실무에서는 둘을 거의 혼용해서 씁니다. 이스타가 "Reconciliation 안의 비교 알고리즘이 diffing 아닌가?"라고 물으면 — 그게 정확합니다.

리액트 공식 문서도 "Reconciliation" 챕터 안에 diffing 휴리스틱을 설명해요. 같은 큰 우산 아래 있다고 보면 됩니다.

정리

일반 트리 비교       : O(n³)  (노드 이동 추적 + 부분 트리 비교)
                       ↓
리액트의 휴리스틱     : "같은 위치만 비교, 타입 다르면 통째 교체"
                       ↓
Diffing 알고리즘     : O(n)
                       ↓
Reconciliation       : 그 결과를 실제 DOM에 반영
                       ↓
리스트의 위치 추적    : key prop으로 보강

레이아웃 스레싱을 어떻게 원천차단하는가?
가상 DOM이 자체적으로 batching + 읽기/쓰기 분리 처리
React에서 DOM 측정이 필요하면 ref + useLayoutEffect 조합을 씁니다.
React가 보장하는 순서:
  1. Render Phase 끝       (변경 계산 완료)
  2. Commit Phase 끝       (모든 DOM 변경 적용 완료)
  3. useLayoutEffect 실행   (이때 DOM 측정)
                          ← 한 번의 layout 발생 (정상)
                          ← 모든 React 변경이 이미 적용된 상태
                          ← 그러니 "최신값"이 이미 결정되어 있음
핵심: "쓰기를 다 끝낸 다음에야 읽기" 라는 순서가 React 구조 자체로 강제됨. 이게 직접 DOM 조작 코드와의 결정적 차이.

1. 첫 렌더    : width=0으로 div를 그릴 가상 DOM 생성
2. Commit     : 실제 DOM에 div 부착 (이때 ref.current 채워짐)
3. useLayoutEffect 실행 : offsetWidth 측정 → setWidth(400) 같은 식
4. 두 번째 렌더 : width=400으로 다시 그릴 가상 DOM 생성
5. Commit     : 실제 DOM 갱신
6. Paint      : 사용자에게는 width=400만 보임
                (1~5는 paint 전에 모두 끝나므로 깜빡임 없음)
