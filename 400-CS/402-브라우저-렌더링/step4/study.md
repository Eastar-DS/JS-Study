## 정리
Render Tree는 DOM과 CSSOM을 합쳐서 실제 화면에 그릴 노드만 모아 만든 트리입니다.

# 02Layout

## 정리


## 질문
1. Layout 단계는 무엇을 계산하나요?
=> 랜더트리에 있는 요소가 x,y가 어디에 위치해야하는지, 정확한 너비는 얼마나 되는지 등
2. 어떤 요소의 높이가 바뀌면 왜 다른 요소의 위치도 바뀔 수 있나요?
=> 해당 요소의 높이가 바뀌면 다른요소가 위치해야하는 x,y좌표가 달라질 수 있기 때문
3. `width: 50%`는 왜 Layout 단계에서 실제 px 값으로 계산되어야 하나요?
=> 나도 그게 궁금해. 일단 무조건 단위는 px를 입력해야하는거같고, 50%는 부모의 너비를 기준으로 50%라는거니까 정확한 px값이 뭔지를 몰라서 그렇다고 생각해.

Q1. Layout 단계에서 브라우저가 정확히 무엇을 계산하나요?
    한 문장 정의를 적어주세요.
=> 요소가 위치해야하는 x,y 좌표와 너비, 높이 등 px value.

Q2. `<p>1</p><p>2</p><p>3</p>` 가 있을 때, 첫 번째 p의 font-size를 키우면
    왜 두 번째, 세 번째 p의 위치도 바뀌어야 하나요?
    Layout의 어떤 특성 때문인가요?
=> font-size를 키우면 높이나 너비가 달라질거고, 이에따라 연관되어있는 요소들의 위치 x,y를 다시계산해야함. 레이아웃은 주변 요소의 영향을 받는 특성때문.

Q3. 자가 질문 종합: "왜 레이아웃이 자원을 많이 소모하는가?"에
    이번 챕터까지 본 내용으로 답해보세요.
    (한 문장으로 정리. 의존성, 연쇄, 환경 같은 키워드를 써도 OK)
=> 참 어려운 질문임. 일단 레이아웃은 서로 연결된 요소들을 모두 고려하면서 요소들의 위치와 크기를 계산해야하므로 복잡함. 또한 랜더트리만 가지고 바로 레이아웃과정을 진행할 수 있는것도 아니고, Computed Style과정이 또 필요함. 

점검 질문 (스스로에게 — "오늘 가장 답하기 어려웠던 질문" 후보)
Layout이 끝나면 각 요소의 위치와 크기를 알게 됩니다. 그런데 아직 그릴 수 있는 상태가 아닙니다. 무엇이 더 필요할까요?
=> 와. 상상도 못한 어려운 질문이다. 레이아웃까지 끝났는데 왜 아직도 그릴 수 없는거지? 도저히 모르겠음.

# 03 Paint

## 정리
Layout이 끝나면 브라우저는 요소의 크기와 위치를 압니다.
하지만 위치와 크기만으로는 화면이 보이지 않습니다.
```text
버튼이 x=20, y=20, width=100, height=40이라는 것은 알았다.
그런데 배경색은?
글자색은?
테두리는?
그림자는?
```
이 시각 정보를 실제로 그리는 과정이 Paint입니다.
Paint를 아주 단순화하면 "어떤 위치의 픽셀을 어떤 색으로 칠할지 정하는 일"입니다.


## 질문
1. Layout과 Paint의 차이는 무엇인가요?
=> Layout : x,y위치와 너비나 높이등 계산. Paint : 레이아웃에서 계산된 위치와 너비나 크기만큼 어떤 색상을 칠할지 결정.
2. 버튼의 `width`, `height`, `background-color`, `box-shadow` 중 Layout과 더 관련 있는 것은 무엇이고 Paint와 더 관련 있는 것은 무엇인가요?
=> Layout : width, height, Paint : background-color, box-shadow
3. Paint 비용이 커질 수 있는 CSS 속성에는 어떤 것들이 있나요?
=> 앗 읽고 넘어가서 기억이 안남. 다시 가져오면 : box-shadow, text-shadow, filter, border-radius, 배경 이미지

Q1. Layout이 끝났는데 왜 아직 화면이 안 그려지나요?
    Paint가 무엇을 추가로 결정하나요?
    (자기 점검 질문이었던 것 — 자료 읽고 자기 언어로 답하기)
=> 계산된 위치와 크기에 색상 결정
Q2. 아래 CSS에서 "Layout과 관련 큰 속성"과 "Paint와 관련 큰 속성"을
    각각 분류해보세요.

    .card {
      width: 300px; => Layout
      height: 200px; => Layout
      margin: 16px; => Layout
      background-color: white; => Paint

      box-shadow: 0 2px 8px rgba(0, 0, 0, 0.1); => Paint
      color: black; => Paint
    }

Q3. 어떤 CSS 속성을 바꾸면 "Layout 없이 Paint만 다시 일어날 가능성이 큰가요"?
    예시 1~2개 적어주세요.
    (왜 그런가 한 줄로 설명)
=> backgroud-color, color : x,y좌표나 크기변환없이 픽셀의 색상만 변환.

=> 그려야하는 위치와 크기, 색상이 결정되었는데 뭐가 더 필요할까? 잘 모르겠음. Composite라는 단어를 보아도 잘 모르겠는데, 합성해야하는 무엇인가가 있는건가?

## 보완 노트
DOM
  +
CSSOM
  ↓
Computed Style 적용 (상속, 우선순위, 단위 변환 일부)
  ↓
Render Tree   ← 이미 색상 정보 포함
  ↓
Layout        ← width/height 같은 환경 의존 값을 used value로 (px)
  ↓
Paint         ← Render Tree + Layout 결과를 바탕으로 그리기 명령 생성


# 04 Composite

## 정리
브라우저는 모든 것을 하나의 평면에 한 번에 그리지 않을 수 있습니다.
일부 요소는 별도의 레이어로 분리될 수 있습니다.

브라우저는 특정 요소를 별도 레이어로 다루면, 전체 페이지를 다시 그리지 않고 레이어 위치만 합성해서 화면을 갱신할 수 있습니다.



## 질문
1. Composite는 무엇을 하는 단계인가요?
=> 그려야하는 여러 레이어를 합성하는 단계
2. `transform` 애니메이션이 `left` 애니메이션보다 유리할 수 있는 이유는 무엇인가요?
=> left 애니메이션은 레이아웃단계부터 다시 시작해야하지만 transform은 컴포짓 단계만으로 리랜더링이 가능해서.
3. Layout, Paint, Composite 중 가장 뒤쪽 단계만 다시 일어나는 것이 왜 성능에 유리할까요?
=> 앞쪽단계가 다시 일어나면 뒤쪽단계는 다시 일어날 가능성이 매우 높아서(거의 반드시 다시 일어날것 같다고 생각됨)

Q1. Composite는 무엇을 합치나요?
    그리고 왜 모든 요소를 한 평면에 한 번에 안 그리고 레이어로 나누나요?
=> 여러 레이어를 합성하는 단계. 왜 여러 레이어로 나눌까? 아래 나의 질문처럼 어떻게 여러 레이어로 나누는 기준을 가지고 있을까? 딱보기에도 여러 레이어로 나누는게 좋다고 직관적으로 느껴지는 경우는 있음. 예시로 들어준 본문, 오버레이, 모달같은경우.

Q2. 어떤 애니메이션이 더 부드러울 가능성이 클까요? 이유와 함께.

    A: .box { left: 100px; }
    B: .box { transform: translateX(100px); }
=> B. Composite단계만 다시 일어날가능성이 높으므로 리랜더링에 걸리는 시간이 줄어든다.

Q3. 다음 세 가지 변경을 비용 순서대로 정렬해보세요. 비싼 것부터.

    1) box.style.width = "300px";
    2) box.style.transform = "translateX(50px)";
    3) box.style.backgroundColor = "red";

    (Layout/Paint/Composite 중 어느 단계가 다시 일어나는지 함께 적기)
=> 1(Layout) > 3(Paint) > 2(Composite)
